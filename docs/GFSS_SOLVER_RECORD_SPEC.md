# GFSS Solver Record v1

GFSS Solver Record is the canonical benchmark interchange format for solver-level experiments.

## Purpose

Every solver candidate should be comparable on the same axes without relying on ad-hoc console logs. A record captures correctness, time-to-verified-solution, peak solver memory, algorithmic work, hardware/context, and enough provenance to reproduce the point.

The primary visualization is the **upper-left Pareto frontier**:

- x-axis: `timing.total_ms` or an amortized reuse time; lower is better.
- y-axis: `memory.capacity_mdof_per_gib`; higher is better.
- only numerically valid runs are admitted to the default frontier.

`memory.peak_bytes_per_dof` remains the canonical engineering storage quantity. `capacity_mdof_per_gib` is derived for visualization.

## Canonical storage

The canonical file format is **JSON Lines / JSONL**. One UTF-8 JSON object is written per line. Recommended extension: `.jsonl`.

Why JSONL rather than CSV as the source of truth:

- records are append-only and streamable;
- old and new schema fields can coexist;
- nested work/provenance/hardware data remain self-describing;
- a single line can be pasted or uploaded to ChatGPT without surrounding context;
- CSV can be generated as a flat projection when needed.

A JSON Schema is provided at `docs/gfss_solver_record.schema.json`.

## Compatibility contract

- `schema`: must be `gfss.solver_record`.
- `schema_version`: semantic major/minor string. v1 readers must reject unknown major versions and ignore unknown fields from compatible minor revisions.
- Required v1 fields are deliberately small. New optional telemetry may be added without changing the major version.
- Units are encoded in field names. Do not silently change units.
- Missing measurements are omitted or `null`; never invent zero for an unmeasured quantity.
- Derived fields may be regenerated by tooling. Raw measured fields take precedence.

## Record identity and provenance

Each record contains:

- `run_id`: unique human/tool-generated identifier.
- `timestamp_utc`: ISO-8601 UTC timestamp.
- `git.commit`: source commit SHA when known.
- `git.branch`: branch when known.
- `benchmark`: executable/test that produced the record.
- `solver.family`: broad algorithm family, e.g. `jacobi_pcg`, `mixed_refinement`, `geometric_multigrid`, `aggregation_multigrid`.
- `solver.variant`: implementation/configuration identifier.
- `problem.name`: canonical benchmark case name.

A point is only directly comparable with another when problem definition, requested tolerance, correctness policy, and material/discretization assumptions are compatible.

## Correctness gate

The default Pareto plot admits a run only when all of the following are true:

1. `correctness.converged == true`
2. `correctness.true_relative_residual <= correctness.target_relative_residual`
3. no fatal numerical breakdown is recorded

Recursive/estimated residuals may be logged in `extra`, but they never own correctness. The true/audited residual remains the gate.

## Timing

Required solver timing fields:

- `timing.setup_ms`: one-time solver/preconditioner setup.
- `timing.solve_ms`: solve phase for the measured RHS.
- `timing.total_ms`: canonical single-RHS time. Normally `setup_ms + solve_ms` unless the benchmark explicitly measures a different end-to-end interval.

Optional:

- `timing.truth_ms`: FP64 verification/audit cost.
- `timing.rhs_reuse_count`: number of RHS assumed for an amortized projection.
- `timing.amortized_ms`: `setup_ms / R + solve_ms` when plotting per-RHS cost under reuse count `R`.

The plotting tool can derive amortized time for arbitrary `R` from setup and solve time, so do not overwrite the raw timing.

## Memory and capacity

Canonical raw fields:

- `memory.peak_solver_bytes`: peak bytes attributable to solver/preconditioner state, excluding the common immutable problem representation unless explicitly stated otherwise.
- `memory.peak_bytes_per_dof`: `peak_solver_bytes / problem.fine_dofs`.

Derived visualization field:

`memory.capacity_mdof_per_gib = 2^30 / peak_bytes_per_dof / 1e6`

Higher is better. This answers: **how many million fine DOFs of this solver state fit in one GiB?**

If an experiment reports only a modeled B/DOF rather than measured allocation, set `memory.kind` to `modeled`; otherwise use `measured`.

## Work ledger

FLOPs are diagnostic, not a primary Pareto objective. Record work explicitly so numerical algorithm quality can be separated from implementation quality.

Recommended counters in `work`:

- `fine_operator_applies`
- `coarse_operator_applies`
- `prolongation_applies`
- `restriction_applies`
- `dot_products`
- `axpy_like_ops`
- `true_residual_audits`
- `fine_matvec_equivalents`
- `useful_flops`
- `estimated_bytes_moved`

`fine_matvec_equivalents` is the preferred hardware-light normalized work metric. For comparable matrix-free levels, a level-l operator application may be weighted approximately by `n_l / n_0`; exact definitions must be documented by the producer when different.

Derived arithmetic intensity when both counters exist:

`work.arithmetic_intensity_flop_per_byte = useful_flops / estimated_bytes_moved`

Profiler-derived physical traffic and FLOPs should be placed under `profiler`, not used to overwrite algorithmic estimates.

## Derived convergence metrics

For a run with initial true relative residual `r0` and final true relative residual `r`:

`derived.residual_digits_removed = max(0, -log10(r / r0))`

Useful secondary metrics:

- `derived.digits_per_second = digits_removed / (solve_ms / 1000)`
- `derived.time_memory_burden_ms_bpd = total_ms * peak_bytes_per_dof` (lower is better)
- `derived.digits_per_second_per_bpd = digits_per_second / peak_bytes_per_dof` (higher is better)
- `derived.digits_per_fine_matvec_equivalent = digits_removed / fine_matvec_equivalents`

These are secondary rankings only. The authoritative optimization view is still the multi-objective Pareto frontier.

## Hardware/context

Minimum useful hardware fields:

- `hardware.cpu`
- `hardware.gpu`
- `hardware.gpu_vram_bytes`
- `hardware.openmp_threads`
- `hardware.precision_policy`

Optional compiler, CUDA, driver, clock/power mode, and profiler context can be added under `hardware` or `extra`.

## File layout

Recommended local layout (result files are not source-controlled by default):

```text
results/
  solver_records.jsonl
  exports/
    solver_records.csv
    pareto.png
```

## Plotting convention

Default plot:

- x = time to true tolerance in milliseconds (lower is better)
- y = capacity in MDOF/GiB (higher is better)
- valid candidates only
- Pareto frontier = upper-left non-dominated envelope
- failed/invalid runs may optionally be shown separately but never connected to the frontier

For RHS reuse `R`, the x value is:

`setup_ms / R + solve_ms`

Use the same y-axis because the retained solver/preconditioner state is unchanged.

## Integration rule for future benchmarks

Every solver-level benchmark should eventually emit one `GFSS Solver Record` for each complete candidate/problem/configuration tuple. Microbenchmarks that do not produce a verified solution (operator throughput, transfer kernels, isolated coarse-storage audits) should **not** masquerade as solver records; they may use their own telemetry and feed solver records later.

A benchmark may print human-readable console output and additionally print exactly one line prefixed with:

```text
GFSS_RECORD_JSON=
```

followed by the compact JSON object. The helper in `include/gfss/solver_record.hpp` implements this convention.
